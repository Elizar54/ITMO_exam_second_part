# ML и LLM-дизайн

## 1. Почему нет обученного классификатора

Для обучения модели классификации тем или «типовой / нетиповой» необходим размеченный датасет. В рамках PoC такого датасета нет, а искусственная разметка нескольких примеров создала бы ложное ощущение качества.

Поэтому PoC использует:

- интерпретируемые risk rules;
- semantic retrieval;
- scope examples;
- metadata документов;
- строгую policy-логику;
- отказ от автоматизации при недостаточных сигналах.

Это честный baseline, который можно заменить обученной моделью после появления данных.

## 2. Scope gate

Scope gate нужен, чтобы вопросы не по сервису не загружали LLM и операторов.

Используются embeddings положительных и отрицательных примеров:

```text
positive: вход, подписка, оплата, приложение, аккаунт
negative: погода, математика, фильмы, перевод, анекдоты
```

Рассчитываются:

- максимальная similarity с positive examples;
- максимальная similarity с negative examples;
- margin между ними.

Результат:

- `IN_SCOPE`;
- `OUT_OF_SCOPE`;
- `UNCERTAIN`.

Пороговые значения являются экспертными assumptions.

## 3. Risk detection

Risk detection реализован правилами, а не LLM.

High-risk категории:

- взлом аккаунта;
- мошенничество;
- неизвестное списание;
- юридическая претензия;
- удаление аккаунта или данных;
- другие заранее запрещённые темы.

Плюсы rules baseline:

- интерпретируемость;
- низкая latency;
- отсутствие сетевой зависимости;
- простое тестирование;
- гарантированная блокировка известных сценариев.

Минус: ограниченный recall для новых формулировок.

## 4. Retrieval

Отдельные коллекции:

- knowledge base;
- response templates;
- service scope examples.

Для каждого запроса анализируются:

```text
top1 score
top2 score
margin = top1 - top2
```

Высокий top1 без достаточного margin может означать неоднозначность.

Абсолютные cosine thresholds зависят от embedding-модели и данных. Значения PoC нельзя переносить в production без валидации.

## 5. Confidence

Система не использует `confidence`, который LLM сама пишет в JSON.

Системная уверенность определяется набором внешних условий:

```text
scope passed
AND low risk
AND retrieval score passed
AND retrieval margin passed
AND document allows auto reply
AND citations passed
AND output guardrails passed
AND audit saved
```

Не используется среднее всех сигналов: сильный компонент не должен компенсировать критически слабый.

Для интерфейса лучше показывать decision trace, а не одно «магическое» число.

## 6. Роль LLM

LLM используется только для генерации ответа по retrieved context.

LLM не должна:

- определять policy;
- разрешать себе автоответ;
- выполнять действия;
- работать с raw PII;
- придумывать документы;
- отвечать без достаточного контекста;
- замещать risk detection.

## 7. Grounding

В prompt передаются document IDs и тексты retrieved chunks.

LLM должна вернуть citations. Валидатор проверяет, что каждая citation входит в список реально переданных документов.

Citation сама по себе не доказывает полную фактическую корректность, но блокирует простейший класс выдуманных источников.

## 8. Output validation

Ответ блокируется при:

- невалидном JSON;
- нарушении Pydantic schema;
- неизвестной citation;
- PII в ответе;
- запросе пароля, OTP или карты;
- заявлении о выполненной операции;
- `needs_operator=true`;
- пустом или слишком длинном ответе.

## 9. Corrective retry

При первой ошибке валидации система выполняет один исправляющий запрос.

Второй prompt содержит конкретные ошибки:

```text
- unknown citation;
- forbidden claim;
- output contains PII.
```

Контекст не расширяется. После второй ошибки — оператор.

Ограничение числа попыток защищает от роста стоимости, высокой latency, циклических ошибок и непредсказуемого поведения.

## 10. Шаблоны

Шаблонный ответ предпочтительнее свободной генерации, когда найдено точное совпадение:

- дешевле;
- быстрее;
- детерминированнее;
- проще аудировать;
- ниже риск галлюцинации.

В текущем PoC шаблоны в первую очередь демонстрируют graceful degradation при недоступности LLM.

## 11. Оценка качества без постоянной разметки

Online F1 и accuracy нельзя честно считать без ground truth.

Доступные сигналы:

- operator acceptance rate;
- доля существенных правок;
- handling time;
- CSAT;
- reopen rate;
- user feedback;
- fallback rate;
- выборочный ручной safety-аудит.

После появления разметки можно оценивать:

- recall high-risk класса;
- precision автоответов;
- macro-F1 по темам;
- calibration;
- retrieval Recall@k;
- answer groundedness.

## 12. Подбор порогов

Production-процесс:

1. Собрать исторические тикеты.
2. Обезличить данные.
3. Разметить scope, risk, relevant documents и результат.
4. Разделить train/validation/test по времени.
5. Построить curves automation coverage, precision automated decisions, unsafe rate и operator rate.
6. Выбрать thresholds под ограничения бизнеса.
7. Проверить стабильность по каналам и категориям.
8. Провести shadow pilot.

## 13. Drift

Без ground truth можно отслеживать:

- распределения embedding scores;
- top1/top2 margin;
- долю `UNCERTAIN`;
- долю fallback;
- новые слова и коды ошибок;
- рост out-of-scope;
- изменение длины обращений.

Это не заменяет оценку качества, но помогает выявить изменение входящего потока.

## 14. Ограничения

- искусственные scope examples;
- маленькая KB;
- экспертные thresholds;
- rules имеют ограниченный recall;
- embeddings могут путать близкие бизнес-сценарии;
- citations не гарантируют отсутствие всех галлюцинаций;
- внешний LLM может менять поведение между версиями.
